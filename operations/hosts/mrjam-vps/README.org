* Résultat et portée

La configuration du VPS est désormais disponible comme code reçu vérifié.
Le socle matériel/réseau est reconstruit dans =machine.nix= à partir de ce code,
et non de Spectre. Douze faits sont rapprochés automatiquement des littéraux
originaux. =stateVersion = "26.05"= provient de la ligne 16 du fichier machine
reçu ; il n'est pas déduit d'une version NixOS ou d'un pin nixpkgs. Les UUID,
MAC, adresses, routes, résolveurs, périphérique GRUB et clé publique root sont
des déclarations du code remis, sans prétendre authentifier l'état courant.

=configuration.nix= est un point d'entrée explicite de préparation. Il ne
constitue pas encore l'ensemble des services du VPS. Son assertion bloquante
interdit toute construction de =system.build.toplevel= jusqu'à fermeture et
qualification de cette composition. Supprimer cette assertion ou ajouter un
booléen « approuvé » ne remplace pas les contrôles manquants.

Le flake expose les modules et leurs tests ; aucune =nixosConfiguration= de
production partielle n'est publiée. L'objectif de mise en service est autorisé
par [[file:../../mise-en-service/mandat.org][le mandat courant]] ; aucun nouveau gel général n'est invoqué.

Le lot suivant ajoute les modules exécutables Forgejo, Kanidm et Nextcloud,
ainsi que la construction ViSe et son adoption sans DDL au redémarrage.
Le détail courant, les refus et les limites de leurs essais sont dans
[[file:../../runtime/ADOPTION-SERVICES.org][le dossier d'adoption des services]]. Les qualifications historiques
ci-dessous conservent leurs références ; elles ne sont pas réattribuées aux
nouveaux fichiers.

La composition PostgreSQL conserve exactement la politique hôte après les
blocs dédiés. Les modules ne peuvent plus se disputer la première position.
Le rôle et la base =etp_carnet= sont refusés dans les capacités Rust. ViSe
utilise le socket Unix et peer, rejette les autres bases pour son rôle et
rejette son rôle sur IPv4/IPv6 TCP. Les qualifications ne prétendent pas
remplacer l'analyse des privilèges SQL existants ou du reste de la politique.

Le module Nextcloud conserve la désactivation de l'upload progress dans PHP
global, CLI et le pool FPM, ainsi que les conditions persistantes de FPM/cron
sur =/var/lib/nextcloud-php-security/blocked=. Il refuse PHP antérieur à 8.4.27
ou d'une autre branche que 8.4. Ce minimum préserve le correctif déclaré ; ce
n'est pas une preuve du build PHP actif. Les tests utilisent explicitement
une étiquette de version synthétique et ne construisent pas ce paquet.

Le contrat ViSe consulté est celui de
=MrJ-am/etp-vie-affective@65bbd8c53a1f6d2efda453a5c82d66c49df26699:deployment/CONTRAT-VPS.md=.
Il confirme l'indépendance et la persistance SQL + registre d'effacement.
La version de l'application installée ne découle pas de cette référence.
Le module neuf supprime l'import flottant =<nixpkgs>= et l'import dynamique
=target.baselineConfiguration= du précédent adaptateur. Il n'exécute pas
=vise-provision= et n'utilise pas les cibles privées non remises.

Le script de sauvegarde reçu effectue un dump puis une copie du registre,
utilise =set -eu= sans =pipefail= et vérifie seulement la liste du dump.
Cela ne prouve ni une capture cohérente, ni une restauration. Une sauvegarde
ViSe nouvelle reste donc refusée par le module tant que ces contrats ne sont
pas qualifiés ; aucune sauvegarde existante n'a été touchée.

La capacité SSH actuelle n'accepte que l'inventaire V1 épinglé. Les observations
complémentaires ci-dessus sont des propositions de contrats, pas des commandes
à lui transmettre. Une extension doit être un nouveau paquet fermé, testé,
relu et adopté séparément. Elle n'accepte aucun chemin, shell, requête SQL ou
nom de service libre. Ne pas relancer V1/V2/provenance pour obtenir ces champs.

* Ordre exact des étapes et retour

1. Fermer et évaluer la nouvelle composition complète dans ce dépôt. Préserver
   PostgreSQL, Nextcloud, Kanidm, Forgejo, ViSe et leurs états ; remplacer les
   dépendances historiques par les sources et artefacts retenus. Les champs
   expurgés doivent devenir des références de gestion locale, pas des valeurs
   factices ou des secrets dans le store.
2. Construire les artefacts et la génération dans Cloud, puis qualifier la
   même fermeture, les règles, les budgets, les migrations et le retour. Lier
   commit propre, arbre, verrous, NAR, manifeste des migrations, ressources Elm
   et références de secrets dans une livraison immuable.
3. Réaliser la revue indépendante de cette livraison. Le dossier actuel la
   prépare ; les résultats locaux ne sont ni une signature protégée ni cette
   revue. L'approbation opérationnelle porte sur ces identifiants exacts, la
   cible, les effets, la fenêtre maximale de trois heures et le retour.
4. Avant installation, vérifier sur place la correspondance de génération,
   les identités adoptées et l'accès d'administration existant. Conserver une
   session administrative et un chemin de retour contrôlé sur Spectre ; Cloud
   n'en reçoit pas l'accès. Ne pas relancer l'installateur impératif.
5. Installer exactement les fermetures qualifiées par le mécanisme borné retenu.
   Toute divergence d'identifiant, NAR, état initial ou précondition arrête la
   procédure. Aucun build candidat, téléchargement flottant ou script libre
   ne s'exécute pendant la bascule.
6. Pour la migration initiale : fermer les écritures et tâches concernées,
   drainer, produire la capture cohérente qualifiée, appliquer uniquement les
   migrations prévues, vérifier le candidat sur ressources synthétiques isolées,
   puis effectuer le changement de route explicite. ViSe conserve son contrat
   autonome ; sa base et son registre d'effacement forment une unité cohérente.
7. Contrôler états, refus, contrats HTTP et drainage par sorties fermées. Ne
   retirer l'ancienne fermeture qu'après expiration de la période de retour.
   Si un critère échoue avant l'échéance d'abandon, exécuter le retour qualifié.
8. Le retour applicatif réinstalle le binaire et le routage compatibles avec le
   schéma courant. Si une migration n'est pas compatible en arrière, appliquer
   la procédure de données séparée déjà répétée, en préservant les écritures
   et effacements intervenus. Une ancienne génération NixOS seule ne suffit pas.

Les identifiants de génération complète, de livraison et de contrôleur de
production n'existent pas encore pour cette composition. Il serait trompeur
de donner maintenant une commande =switch= ou une procédure de restauration
exécutable avec des placeholders. Le travail restant est explicite ci-dessus ;
aucune de ces opérations de production n'a été lancée dans Cloud.
