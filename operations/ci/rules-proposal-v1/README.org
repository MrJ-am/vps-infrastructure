* Droits et secret technique

L'identité technique déjà attestée reste l'auteur de la proposition ; aucune
identité humaine n'est imitée. Le bail reprend le verrou, les contrôles de
configuration, le binaire Forgejo17 et les commandes bornées du bootstrap
qualifié, dans une variante distincte. Aucun compte ni mot de passe n'est créé.

La CLI native Forgejo17 crée encore des jetons avec =ResourceAllRepos=true=,
y compris lorsqu'on limite leurs scopes. Avant le premier appel API ou Git,
une transaction fixe limite le jeton fraîchement créé au seul dépôt des règles :
ressource unique dans =access_token_resource_repo=, puis =resource_all_repos=false=.
Les scopes sont uniquement =read:user,write:repository=. L'identité, le nom
aléatoire du bail, les scopes et le dépôt privé unique sont vérifiés dans la
transaction. Aucun corps de dépôt, secret ou autre compte n'est lu par ce SQL.

La révocation retire les ressources du seul jeton de ce bail puis le jeton,
dans une transaction, et vérifie ensuite le refus HTTP401. Un journal privé
permet la révocation au prochain essai après interruption. Les autres jetons
et leurs ressources restent intacts. Le jeton n'entre jamais dans argv,
l'environnement, un fichier, un journal public ou la sortie de l'agent.

Ces choix correspondent aux modèles natifs Forgejo17
=models/auth/access_token.go= et =access_token_resource.go= du pin
=/nix/store/prakx1jzmkn4vaw6wj404njghaq3klyb-source=. La route de création
de PR appartient au scope repository ; aucun scope organization ou issue
supplémentaire n'est nécessaire.

Forgejo17 retire aussi =AllowAdminOverride= aux jetons limités à un dépôt.
La lecture API des protections exige ce privilège et refuse donc ce jeton.
Le helper conserve cette restriction : une requête fixe =READ ONLY= compare
les 24 colonnes de la protection native à la règle qualifiée, exige l'unique
dépôt et l'unique règle =main=, et ne retourne qu'un booléen. Les listes vides
et nulles sont normalisées comme dans la projection API qualifiée. Toute
règle supplémentaire ou dérive est refusée. Aucun jeton plus large n'est créé
pour lire ces métadonnées ; aucune protection n'est modifiée.

* Concurrence et reprise

L'entrée n'accepte aucun argument. Elle exige la génération active et le boot
=phi68cwg38madbq8p805yvrsyry8g8wr=, le checkpoint OPEN et le résultat terminal
réussi de la bascule005, sous le verrou transactionnel existant. Elle conserve
ce verrou pendant le bail de proposition.

Les protections de main, sa révision, la visibilité privée et Actions désactivé
sont relus avant et après chaque étape utile. Le Git client reçoit uniquement
un bundle scellé et l'URL loopback fixe. Le hook pre-push immuable exige l'unique
ref et commit attendus, avec ancien OID distant nul ; le receive-pack vérifie
ce même ancien OID. Aucun force push, suppression ou bypass de hook serveur
n'est utilisé. La maintenance automatique du dépôt temporaire est désactivée.

Une branche déjà identique et la même PR ouverte sont réutilisées. Une branche
différente, une PR modifiée, fermée, fusionnée, d'un autre auteur ou liée à
d'autres révisions sont refusées. Un échec après création de branche ou PR
les laisse en place ; aucune suppression corrective n'est implicite.

* Revue et adoption ultérieures

La PR annonce explicitement que la CI de cette forge n'est pas encore active.
Le hash d'une preuve hors CI ne devient ni un statut CI ni une approbation.
L'examen humain réel et l'adoption initiale des règles relèvent du circuit
distinct prévu par le mandat. Ce paquet ne fournit pas l'opération de fusion
et ne change pas la politique pour faire accepter sa propre proposition.

Le banc Forgejo/PostgreSQL utilise uniquement des comptes, historiques et
objets inventés. Les tests Git de concurrence utilisent aussi des dépôts
inventés. Ces preuves qualifient les nouveaux raccords ; elles n'affirment
aucune PR, revue ou mutation déjà effectuée sur la forge réelle.
