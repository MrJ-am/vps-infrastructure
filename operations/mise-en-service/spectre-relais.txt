1. RETROUVER LA SOURCE VPS DANS LE CODE LOCAL

L'utilisateur confirme que MrJ-am/vps-infrastructure est la source de vérité
souhaitée. Cloud n'y a trouvé qu'une référence NixOS historique inactive avec
des imports manquants. Il faut établir si Spectre possède le checkout/source
VPS réellement utilisé pour la dernière construction.

Dans les seuls emplacements de code de ton espace de travail, repère le checkout
vps-infrastructure déjà présent. Ne parcours pas .ssh, coffres, sauvegardes,
documents personnels, répertoires applicatifs ou historiques de recherches.
Lis les métadonnées Git (HEAD, arbre, branche, statut), sans afficher d'URL
contenant des credentials, et seulement les sources Nix/manifestes de ce VPS.
Ne prends jamais la configuration matérielle de Spectre pour celle du VPS.

Rapporte les références non secrètes suivantes, ou « inconnu » avec raison courte :
- commit et arbre exacts du checkout VPS ; présence de modifications locales ;
- fichier d'entrée et cible nixosConfigurations, si elle existe ;
- system.stateVersion déclaré dans cette source, sans en déduire l'état installé ;
- mécanisme qui lie, s'il existe, cette source à la génération du VPS ;
- référence publiée exacte de ces sources ou liste des SEULS fichiers source

n'existe pas localement, indique ce résultat ; ne contourne pas cette absence
par SSH root ou exploration générale de la production.

L'inventaire V1 a déjà été fait ; ne le relance pas pour remplir les nouvelles
inconnues. Le programme V1 n'accepte que ses trois blobs épinglés et refuse V2.
La clé publique dédiée est déjà fournie, validée et versionnée :

Ne demande ni ne lis la clé privée. Ne régénère pas de clé ou de compte.

Cloud prépare et qualifie operations/bootstrap-observation : un paquet Nix
immuable avec Python et systemd épinglés, sonde V2 inchangée et filtres fermés.
L'opération humaine unique est bin/mrjam-observe-adoption, sans argument.
Elle crée seulement une unité systemd transitoire fixe, exécutée sous le compte
mrjam-inventory existant, sans réseau ni privilèges supplémentaires, avec bornes
de temps/mémoire/tâches. Elle conserve V1, SSH, les services et les données.
Sa sortie n'est rendue qu'après réussite et validation du JSON côté VPS.

N'exécute pas cette opération tant que Cloud n'a pas livré son commit, son chemin
store, son NAR hash, les octets exportés et la preuve de qualification système.
Un paquet construit seul n'est pas une qualification. Cette première reprise
te permet de préparer le côté local en parallèle sans attendre ces éléments.

Le futur import et lancement initial appartiennent à l'administrateur humain
par son canal existant : préparer pour lui une commande FIXE avec les artefacts
qualifiés, jamais une délégation root générale à l'agent. Aucun installer.py reçu
ne doit être relancé. N'accorde pas de shell au compte V1. Un échec ou prérequis
absent doit produire un code fermé, sans journal ou sortie brute transférée.
