#+title: Préparation Kanidm par authentification humaine

* Parcours concret

Après publication, installation et qualification indépendante de l'unité, la
personne disposant des droits Kanidm lance dans son terminal VPS :

#+begin_src sh
sudo mrjam-kanidm-worker-login
#+end_src

Le programme demande le compte autorisé à gérer les comptes de service et les
personnes, puis celui autorisé à gérer les accès. Entrée réutilise le premier
compte si celui-ci cumule ces droits. L'utilisateur s'authentifie personnellement
dans le CLI officiel Kanidm 1.11.2. Rien ne doit être envoyé à l'agent ni copié
dans le presse-papiers, une commande, un document ou une variable d'environnement.

Le client officiel crée un cache neuf sous
=/run/mrjam-kanidm-worker-login/=, root 0700, fichiers 0600. Aucun profil
personnel ni cookie de navigateur existant n'est lu. Une réauthentification est
demandée seulement si les privilèges de cette nouvelle session ne sont pas déjà
actifs pour la durée requise. Le champ purpose sert à choisir ce dialogue ;
il n'autorise aucune action : Kanidm vérifie le bearer original à chaque requête.
Le cache n'est jamais affiché.

Le helper démarre =mrjam-kanidm-worker-provision.service=. L'unité reçoit deux
caches dédiés par LoadCredential, effectue l'opération fixe, révoque ces seules
sessions et n'émet que des codes/booleens fermés. Le CLI interactif s'exécute dans
le terminal humain, jamais dans le journal de l'unité. L'entrée humaine nettoie
ses caches et demande également leur logout, y compris après une interruption
ordinaire. Aucun service applicatif n'est démarré par cette étape.
Le module =provisioning-unit.nix= n'ajoute ni wantedBy ni timer.

Le lecteur administratif exige le montage systemd en lecture seule : répertoire
root:root 0500, deux fichiers root:root 0400 à lien unique. Ce contrat est distinct
du staging 0440 de l'adaptation SMTP. La version 1 confondait ces modes et a été
refusée par le test indépendant de l'unité root. Seule la version 2 corrige cette
lecture, sans modifier l'adaptateur SMTP déjà qualifié. L'ancien paquet
=wnk1kg4jmdpl5c3zbc2wk3sn8y9xwdd0-mrjam-kanidm-worker-provision-1= est conservé
comme preuve historique et ne doit pas être installé pour cette opération.

* Changements exacts et conservation

Le programme refuse paramètres, URL, noms ou filtres libres. Il utilise HTTPS
=127.0.0.1:8443= avec SNI/Host =log.mrj.am=, CA publique exacte, sans proxy ni
redirection. Il ne connaît aucun endpoint de reset, création de groupe,
modification d'ACP, récupération de compte ou lecture de personnes.

| Référence locale root 0600 | Traitement | Capacité |
|---------------------------+------------+----------|
| /var/lib/mrjam-identite/kanidm-admission.token | conservée, jamais réémise | mrjam-admission, onboarding et mail-read existants |
| /var/lib/mrjam-identite/kanidm-cycle.token | créée si absente | mrjam-cycle, mail-read, API token RO 90 jours |
| /var/lib/mrjam-identite/kanidm-replay.token | créée si absente | mrjam-replay, people-admins, API token RW 90 jours ; exclusivement pour l'adaptateur DELETE |

Les deux nouveaux comptes sont gérés par =idm_service_account_admins=. Mail-read
reçoit seulement cycle ; people-admins reçoit seulement replay. Les autres
membres, rôles et politiques ne sont pas remplacés. Un nom occupé par une
personne, un autre gestionnaire, des droits supplémentaires, un token existant
inconnu, expiré ou de mauvaise portée provoquent un refus avant toute nouvelle
mutation. Une reprise conforme ne modifie ni les octets ni les tokens.
Le jeton admission est vérifié et conservé.

Les fichiers sont publiés sans remplacement sous verrou privé et fsync. Une
interruption après émission distante mais avant publication locale complète
fait refuser une seconde émission : l'éventuel token orphelin doit être révoqué
explicitement par son gestionnaire après revue. Aucun secret n'est affiché.
Les fichiers partiels et collisions ne sont jamais écrasés silencieusement.

* Frontière de suppression

Sur instance synthétique, Kanidm stock 1.11.2 refuse le profil DELETE minimal :
son ACP intégré de gestion ne permet pas les classes receiver/target requises
par son schéma, et cette entrée est protégée contre la correction via API.
Les migrations natives excluent également les ACP. Aucune modification du
fournisseur ni contournement de ces protections n'est livré.

Le rôle natif disponible =idm_people_admins= autorise DELETE et aussi des
opérations de gestion/reset. Cette portée plus large est constatée dans le test
réel. Elle reste confinée dans =mrjam-identity-deletion.service=, UID 948/GID 944.
Son seul credential est
=/run/credentials/mrjam-identity-deletion.service/kanidm=.

Le nouveau replay UID 944 reçoit uniquement
=/run/mrjam-identity-deletion/delete.sock=. Le protocole fermé transmet issuer
Kanidm exact et UUID canonique ; il ne peut demander ni liste, reset, groupe
ou token. L'adaptateur est un exécutable Rust distinct avec TLS et pair Unix
contrôlés. Sa qualification indépendante est distincte de celle du provisioning.
Les quatre autres traitements Vision et le broker restent inchangés. La forge
reçoit sources et reçus.

* Autorité et essais

Quinze tests d'auteur couvrent conservation, idempotence, conflits, droits,
caches ambigus, fichiers privés, liens, absence d'écrasement et erreurs fermées.
Ils distinguent les permissions LoadCredential root 0400 du staging 0440, et
refusent un montage modifiable, un autre propriétaire ou des liens supplémentaires.
=qualify_provision.py= utilise un vrai Kanidm 1.11.2 jetable et le CLI officiel
sous PTY avec une CA inventée : login/cache 0600, préparation des deux comptes,
refus cycle/admission, rôle replay plus large explicite, DELETE idempotent,
autres rôles inchangés et révocation des sessions temporaires. Les comptes
techniques synthétiques ont des privilèges déjà actifs ; le choix du dialogue
reauth est testé séparément, sans prétendre simuler une clé de sécurité humaine.
Le reçu systemd indépendant doit être joint avant la commande humaine réelle.

L'utilisateur a confirmé disposer d'un compte administratif utilisable.
Aucun reset, RecoverAccount ou DisableAccount n'existe dans les outils livrés.
Le socket administratif de la fixture concerne seulement sa base neuve inventée
dans un répertoire temporaire privé. Aucune donnée ni capacité réelle n'a été
lue par l'auteur pendant ces travaux.
