* Frontière effectivement installée
L’accès créé n’est pas un compte SSH général muni d’un simple wrapper.

- Compte système dédié, UID et GID non nuls, mot de passe verrouillé et aucune
  appartenance à un groupe supplémentaire.
- Clé Ed25519 dédiée générée sur Spectre ; sa partie privée n’a pas été ouverte
  par les scripts ni affichée. Le nouveau client emploie exclusivement cette clé,
  avec agent SSH désactivé, sans proposer l’identité root.
- Destination et fichiers de clés d’hôte repris de la référence SSH locale =vps=.
  =StrictHostKeyChecking=yes=, aucun ajout automatique de clé d’hôte.
- Nouvelle arborescence =/var/lib/mrjam-inventory-access= détenue par root.
  Le domicile, le répertoire SSH, la clé publique autorisée et le programme
  d’entrée sont détenus par root et non modifiables par le compte.
- Clé autorisée munie de =restrict,command="mrjam-inventory-v1"= : commande
  forcée, sans terminal, redirections TCP, transfert d’agent ou script SSH utilisateur.
- Shell de connexion dédié détenu par root : il refuse le shell libre, les autres
  commandes et les arguments inattendus ; Bash ignore les scripts de démarrage
  hérités. Le programme Python reçoit un environnement minimal et =-I -S=.
- Programme d’entrée détenu par root : une seule opération, aucune sélection
  externe de commande, chemin, service ou schéma. Il accepte uniquement les
  octets correspondant aux longueurs et SHA-256 épinglés des trois fichiers.
- Seul le répertoire =work= de cette nouvelle arborescence appartient au compte.
  Chaque invocation valide crée un sous-dossier privé neuf. Les lots restent
  sur le VPS avec le résultat filtré ; ils ne contiennent aucun fichier de données
  applicatives copié par cette opération.

La politique SSH effective a été contrôlée avant et après création du compte.
Les autres sources de clés, commandes forcées globales, chroots et règles de
groupe incompatibles sont refusées par l’installateur. L’activation de la clé
intervient seulement après validation des droits et appartenances du compte.

* Fichiers techniques et réutilisation
=installer.py= et =runner.py= décrivent les nouveaux fichiers d’accès du serveur.
=acces_borne.py= est le client local ; =test_acces.py= contient les tests.
=ACCES.SHA256SUMS= permet de vérifier les ajouts et le rapport, sans inclure
la clé privée. Les empreintes ne constituent pas une signature.

Le client original de remise manuelle n’est pas adapté au nouveau compte à
commande forcée. Pour une nouvelle observation autorisée, utiliser ce client :

#+begin_src bash
/nix/store/jy00n3jp5xj8s40n1fbldmkcr5n7avxc-python3-3.13.15/bin/python3 -I -S ./acces_borne.py --check-boundary
/nix/store/jy00n3jp5xj8s40n1fbldmkcr5n7avxc-python3-3.13.15/bin/python3 -I -S ./acces_borne.py --run
#+end_src

Le rapport existant est protégé contre l’écrasement : une nouvelle collecte
s’arrête avec =RESULT_ALREADY_EXISTS= tant que ce fichier est présent.
La commande =--install= n’est pas une commande de collecte : ne pas la relancer
pour réutiliser l’accès. Elle refuse un compte ou répertoire déjà existant.
