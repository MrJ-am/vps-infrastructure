Vision et Mateval sont consommés par l'assemblage à des révisions Git précises.
Une modification dans un dépôt composant ne change donc pas à elle seule le
binaire installé. Le consommateur doit intégrer la révision et être reconstruit.
Ce constat décrit les dépendances existantes ; il n'ajoute aucune cascade de
commits ni de règles. Signature et style-mrjam ne sont pas des serveurs.

- Nginx envoie les routes du serveur commun vers =127.0.0.1:38101= (blue).
  Green écoute sur =127.0.0.1:38102= ; ce n'est pas un second VPS.
- Aucun processus du serveur Common Lisp n'a été observé.
- ViSe tourne séparément dans =vise.service= ; Nginx utilise le port =3017=.
- L'identité dispose aussi de son service séparé sur le port =3002=.
- Les chaînes externes GitHub, d'admission, de validation et de promotion
  précédemment installées sont arrêtées. Ne pas les réactiver par simple
  application d'un ancien guide.

Ces observations prouvent quels processus et routages sont présents, pas le
bon fonctionnement de tous les parcours métier ni l'alignement intégral de
la machine sur une branche du dépôt. Plusieurs README de composants décrivent
encore les lots synthétiques d'octobre : leurs phrases « non déployé » ne
constituent pas un relevé actuel du VPS.

* Miroirs GitHub et accès Cloud

Forgejo est la source de référence. Les miroirs sortants vers GitHub sont
configurés le 4 novembre pour les neuf dépôts de l'organisation et pour
=MrJam/Config= vers =MrJ-am/config=. =org-validation= n'est pas concerné.
Chaque miroir transmet toutes les branches et tous les tags à chaque push,
avec un rattrapage toutes les huit heures. GitHub peut être écrasé : effectuer
les modifications sur Forgejo. Une clé SSH dédiée à chaque dépôt permet
l'écriture sur sa seule destination GitHub ; aucun jeton personnel GitHub
n'est installé sur le VPS pour ces miroirs.

Les réglages et la dernière erreur éventuelle sont visibles dans les paramètres
du dépôt Forgejo, rubrique des miroirs. « Synchroniser maintenant » permet de
relancer un miroir. Pour l'arrêter, supprimer le miroir et révoquer sa clé de
déploiement sur GitHub. Le miroir copie Git, pas les tickets, demandes de fusion,
secrets, bases applicatives ou fichiers joints des releases. Le transport SSH
choisi ne réplique pas les objets Git LFS.

L'accès de Codex Cloud par Git/API directement à Forgejo reste à mettre en
place et à tester. Aucune livraison automatique n'est annoncée active.

Le 4 novembre, l'API GitHub des dix dépôts correspondant à la forge ne montrait
aucune exécution en cours ou en file d'attente, aucun workflow actif et aucun
webhook de dépôt actif. Lors de la mise en place des miroirs, GitHub Actions
a aussi été désactivé au niveau des dix dépôts : les branches répliquées ne
doivent pas relancer d'anciens workflows. Cela ne réactive aucune chaîne VPS.

* Entretenir cette documentation

Après une migration, mettre à jour l'état daté et le compte rendu décrit dans
[[file:MIGRATIONS.org][MIGRATIONS.org]]. Conserver les anciens résultats comme historiques, sans leur
attribuer les propriétés de la version suivante. Les secrets, sauvegardes,
exports de production et gros paquets de livraison ne vont pas dans Git.
